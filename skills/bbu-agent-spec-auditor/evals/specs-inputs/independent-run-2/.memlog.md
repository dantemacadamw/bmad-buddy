topic: Crawling and structured website analysis solution
updated: 2026-08-20T11:49

- (direction) Use a staged evidence-led workflow: Map, select, targeted collection, page facts, site aggregation, taxonomy classification, and report generation; reject all-site concatenation followed by one model call.
- (capability) CAP-1: Accept and normalize a website URL, enforce domain checks, and discover candidate links with Firecrawl Map plus titles and descriptions.
- (capability) CAP-2: Classify URLs with rules then lightweight-model fallback, score their information value, and select 5–10 core pages using per-type and global limits.
- (capability) CAP-3: Retrieve focused pages with Scrape and use bounded Crawl only for suitable directories, retaining source metadata and Markdown for later analysis.
- (capability) CAP-4: Clean and section Markdown, then extract page-scoped structured facts whose core claims include verbatim evidence and source URLs.
- (capability) CAP-5: Merge multi-page facts through normalization, conflict handling, page authority, source diversity, and freshness into a confidence-scored site fact table.
- (capability) CAP-6: Select primary and secondary classifications from a controlled taxonomy, then derive tags and Chinese descriptions only from evidenced site facts.
- (capability) CAP-7: Persist site, page, fact, and report records and return a report with categories, functions, users, evidence, sources, confidence, and collection metadata.
- (capability) CAP-8: Process bulk Crawl asynchronously through authenticated idempotent webhooks, per-page extraction, completion aggregation, and retriable failure handling.
- (constraint) Firecrawl owns discovery, rendering, and main-content extraction; the business system owns selection, fact processing, aggregation, and quality control.
- (constraint) Respect robots.txt and do not bypass login, CAPTCHA, or access controls; external links and subdomains are disabled by default for targeted crawling.
- (constraint) The default extraction path retains Markdown and uses the owned LLM; do not default to Firecrawl Scrape JSON mode because classification requires cross-page aggregation.
- (constraint) Stop extending collection once identity, positioning, three core functions, users, use cases, category evidence, and two different source-page types are evidenced.
- (constraint) Production Crawl work is asynchronous; verify HMAC-SHA256 signatures and deduplicate events by webhookId before handling pages or completion.
- (decision) MVP comprises Map, rule-based URL selection, 5–10 Scrapes, Markdown fact extraction, aggregation, controlled-taxonomy classification, Chinese report generation, and evidence URLs; Crawl, PDF, interaction, monitoring, and scale features are phase two.
- (assumption) A maintained controlled taxonomy and normalization dictionaries are available to the classification and aggregation stages.
- (assumption) The existing service can provide durable storage, a work queue, and Firecrawl credentials; this source does not select their concrete implementations.
- (question) Who owns taxonomy and synonym-dictionary curation, versioning, and review for classification changes?
- (question) What threshold, tie-breaker, and human-review path should govern conflicting site facts and low-confidence classifications?
- (question) Which queue, persistence schema migrations, retention limits, and monitoring controls will production use?
