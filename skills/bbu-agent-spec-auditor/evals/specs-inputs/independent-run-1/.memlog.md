- (decision) Keep SPEC.md as the lean five-field kernel; preserve multi-item workflow, configuration, schemas, diagrams, and failure handling in typed companions.
- (capability) CAP-1 intent: accept a website URL and discover same-site candidate pages after normalization and domain checks; success: a map result records up to 1000 deduplicated URLs with title and description metadata while ignoring query-parameter variants.
- (capability) CAP-2 intent: classify, score, and select the pages most useful for website identity and offering analysis; success: deterministic page-type rules and priority scoring choose no more than 10 pages under per-type limits, excluding configured low-value routes.
- (capability) CAP-3 intent: acquire high-quality content from selected core pages; success: each selected URL yields stored main-content Markdown, links, metadata, status, language, timestamps, and failure state, with cached results reused within the configured freshness window.
- (capability) CAP-4 intent: convert acquired page content into traceable analysis chunks; success: navigation, cookie, CTA, footer, image, duplicate, and long legal noise is removed while H1-H3 structure, product content, FAQ, tables, scenarios, users, and source URLs remain in chunks no larger than 5000 characters.
- (capability) CAP-5 intent: extract page-level facts without cross-page inference; success: every core extracted value is either empty when unsupported or linked to a source quote, URL, page type, and field while facts remain distinct from marketing claims.
- (capability) CAP-6 intent: produce a normalized site-level fact table from page evidence; success: synonyms are canonicalized, duplicates and conflicts are handled, and each fact receives a reproducible confidence score based on page authority, evidence clarity, source agreement, freshness, and source diversity.
- (capability) CAP-7 intent: classify a site against a governed category taxonomy; success: the output selects an allowed primary and secondary category with reason, confidence, and evidence IDs and never invents a category outside the supplied candidates.
- (capability) CAP-8 intent: generate factual Chinese tags and descriptions from the approved site fact table; success: the short description is 10-50 characters, the detailed introduction is 200-300 Chinese characters, contains the required content sequence, cites source page types, and introduces no unsupported or promotional claims.
- (capability) CAP-9 intent: persist and return an auditable website report; success: the report includes identity, categories, tags, descriptions, functions, users, sources, evidence, per-field confidence, crawl counts, and report version, backed by site, page, fact, and report records.
- (capability) CAP-10 intent: stop acquisition when evidence is sufficient and expose incomplete analysis; success: expansion stops only after the required identity, positioning, at least three functions, users, scenarios, category evidence, and two different source-page types are present, otherwise the run records what is missing.
- (constraint) Firecrawl owns page discovery, rendering, and main-content extraction; the business system owns URL selection, page classification, content cleaning, fact extraction, aggregation, taxonomy matching, and quality control.
- (constraint) The MVP must use Map then targeted Scrape of 5-10 core pages; it must not perform an unrestricted full-site crawl followed by one monolithic model request.
- (constraint) Default page-type limits are homepage 1, about 1, product list 2, product detail 5, solution 2, pricing 1, case study 1, and docs, blog, contact, and legal 0, with a global maximum of 10.
- (constraint) URL priority begins from the documented page-type weights, adjusts for core and noise terms, and penalizes path depth beyond two segments.
- (constraint) Page extraction uses self-managed LLM prompts over cleaned Markdown rather than Firecrawl JSON extraction, because site classification requires cross-page evidence aggregation and re-analysis without re-scraping.
- (constraint) Every core fact and classification must remain traceable to evidence IDs, exact source quotes, source URLs, and page types; unsupported values are empty rather than inferred.
- (constraint) Classification is selection from a maintained taxonomy, not open-ended generation.
- (constraint) Robots rules, authentication, CAPTCHA, and permission boundaries must not be bypassed; external links and subdomains remain disabled by default.
- (constraint) Transient HTTP 408, 429, 500, 502, 503, and 504 failures retry with bounded exponential backoff and jitter; other client errors surface without retry.
- (constraint) Generated copy must avoid unsupported facts and promotional superlatives such as leading, best, or first.
- (decision) Use Scrape for known core pages, Crawl only for directory-like paths or incomplete Map discovery, Interact only for required page actions, and PDF parsing only when enabled for selected documents.
- (decision) When Crawl is introduced, process it asynchronously through signed webhooks, verify HMAC-SHA256, deduplicate webhookId, store each crawl.page result, and aggregate only after crawl.completed.
- (decision) Persist at least sites, pages, facts, and site_reports entities with raw evidence and versioned report output.
- (decision) Defer Crawl and webhooks, PDF parsing, JavaScript interaction, multilingual normalization, monitoring, incremental crawling, bulk queues, and a human-review admin interface beyond the MVP.
- (question) Which complete, versioned primary and secondary category taxonomy is authoritative for CAP-7? The source provides examples but not the production catalog.
- (question) What numeric confidence or completeness thresholds separate automatic acceptance, expansion crawling, partial output, and human review? The source names required fields but no decision thresholds.
- (question) Should failed or conflicting reports be returned as partial results, rejected, or routed to a review state? The source defines evidence and retries but not the product-level disposition.
